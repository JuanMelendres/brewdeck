## Recently Worked On

- Case-insensitive emails + AI coffee ownership (backend, branch `fix/case-insensitive-email-and-ai-coffee-ownership`, 2026-09-24) — audit findings 6 and 3. `Juan@x` and `juan@x` could register as two accounts. New `EmailAddresses.normalize` (trim + `toLowerCase(Locale.ROOT)`) runs in the compact constructors of `RegisterRequest`/`LoginRequest`/`ForgotPasswordRequest` and in `AdminBootstrap`. Flyway V18 aborts the deploy if existing rows differ only by case (no silent merge), otherwise lowercases them and adds `CHECK (email = lower(trim(email)))`, so the existing `UNIQUE(email)` becomes case-insensitive (guard verified on a throwaway Postgres 16: duplicates → RAISE, data untouched; clean → normalized). Old mixed-case JWT subjects stop resolving after deploy; the client's refresh (keyed by user id) issues a lowercase token. `RecipeSuggestionService` now loads the coffee with `findByIdAndOwnerId` (latent IDOR while the AI flag is off). Tests: `EmailNormalizationIntegrationTest`, `EmailAddressesTest` (incl. Turkish locale), `AdminBootstrapTest`, `RecipeSuggestionServiceTest`.
- Validation limits aligned with the DB (full-stack, branch `fix/align-validation-with-db-limits`, 2026-09-24) — audit findings 5 and 12. Valid input used to fail at the DB with a 409 (`roastLevel` 51–80 chars into `VARCHAR(50)`, `grindSetting`/`actualGrind` 81–120 into `VARCHAR(80)`, grams ≥ 10000 into `DECIMAL(6,2)`), and passwords over 72 bytes crashed BCrypt with a 500. Flyway V17 widens the three columns to the limits the API and frontend already promised (metadata-only in PostgreSQL); `RecipeRequest` grams gain `@DecimalMax("9999.99")`; new `@MaxUtf8Bytes` constraint (bytes, not chars) caps passwords at 72 bytes on register/login/change/reset. Frontend Zod mirrors both (`fitsPasswordByteLimit` via `TextEncoder`). Tests: `ValidationLimitsIntegrationTest` (11), `MaxUtf8BytesValidatorTest`, `authSchema.test.ts`, recipe schema. Backend 437 + web 290 green. `database-design.md` migration table brought up to V17.
- MVC error statuses (backend, branch `fix/mvc-errors-return-proper-status`, 2026-09-24) — audit finding 11. `GlobalExceptionHandler`'s catch-all turned Spring MVC client errors into 500s (verified: wrong method, unknown path, `text/plain` body all returned 500), and it logged nothing, so real 500s were invisible. The catch-all now detects Spring's `org.springframework.web.ErrorResponse` contract and keeps its status + headers (405 + `Allow`, 404, 415, 406, 400, `ResponseStatusException`) in the standard `ErrorResponse` body. Real unexpected exceptions are logged with a stack trace (`log.error`, CR/LF-stripped URI) while the body stays generic. Tests: `MvcErrorHandlingIntegrationTest`, `GlobalExceptionHandlerTest` (log capture, header propagation, log-forging guard). `./mvnw clean verify` 424 green. Docs: `architecture/api-design.md` status table.
